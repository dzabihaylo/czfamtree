# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2 (Canvas, Nodes & Edit). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Source of truth:** `design_handoff_family_tree/source/styles.css` (handoff `:root` CSS variables) + REQUIREMENTS.md CANV/NODE/EDGE/SEL/PANEL/SAVE/ERR/DESIGN entries. Per PROJECT.md DESIGN-03, Tailwind v4 `@theme` maps handoff tokens 1:1 — no drift permitted.
>
> **Phase 2 UI surfaces in scope:**
> 1. Canvas viewport below 52px topbar (pan + ⌘-wheel zoom + trackpad pinch)
> 2. Dotted grid background that pans + scales with the canvas transform (world-anchored, not screen-anchored)
> 3. Derived SVG edge overlay (one `<svg>` covering all spouse + parent-child paths)
> 4. `PersonNode` compact 180×76 card (avatar + gender accent stripe + name + birth–death years, is-me ribbon)
> 5. Selection (click, Esc, Enter-to-panel), drag-to-reposition (drag-end commits to server + history)
> 6. Side panel (380px right-docked, Identity + Life + Relationships + Actions + Footer sections)
> 7. Save-state pill in panel header (idle → dirty → saving → saved | error state machine)
> 8. Error toast + red pill when server save fails
> 9. Lucide icon swap for handoff inline SVGs
>
> **Phase 2 surfaces OUT of scope (deferred):**
> - Radial add menu + add-relative flow → Phase 3
> - Undo/redo wiring of drag + edits → Phase 3 (Phase 2 lands the mutations; Phase 3 wires them into `zundo` history)
> - Bottom toolbar pill (undo/redo/zoom/fit/tidy buttons) → Phase 3
> - Toast infra → Phase 3 (Phase 2 hand-rolls a single "Couldn't save" toast inline, scoped to save errors)
> - Search palette → Phase 3
> - Tidy / dagre layout → Phase 4
> - Share modal, presence, live cursors → Phase 5

## Interaction Contract

### 1. Canvas coordinate system

- **World space:** `people[].x` and `people[].y` are unbounded integers in an infinite world. Origin `(0, 0)` is arbitrary; the seed YOU person is inserted at `(0, 0)` by the Phase 1 bootstrap.
- **Screen space:** viewport pixels below the 52px topbar and left of the 380px side panel (when open).
- **Transform:** screen = `translate(transform.x, transform.y) * scale(transform.k) * world`. In CSS, `.canvas-inner { transform: translate(${tx}px, ${ty}px) scale(${k}); transform-origin: 0 0 }`.
- **Initial viewport:** `{ x: 400, y: 180, k: 1 }` places world origin `(0,0)` at screen `(400, 180)` — seed node appears center-upper area of viewport on typical 1440×900 screen.
- **Fit-to-view (CANV-05):** Identical to initial viewport. Phase 2 does NOT implement bbox-fit (auto-zoom-to-content); that lands Phase 3 with the toolbar. CANV-05 says "resets to `{x:400, y:180, k:1}`" — this is a reset-to-default, not a fit-to-content.

### 2. Pan (CANV-01, CANV-03)

| Trigger | Behavior |
|---------|----------|
| MouseDown on empty canvas (not on `.node`, `.side-panel`, `.topbar`) | Enter panning mode: `cursor: grabbing`, record `panStart = { clientX, clientY, tx, ty }`. Deselect any selection. |
| MouseMove during pan | `setTransform({ ...t, x: panStart.tx + (clientX - panStart.x), y: panStart.ty + (clientY - panStart.y) })`. No scale change during pan. |
| MouseUp | Exit panning mode; `cursor: grab`. No persistence (transform is client-only ephemeral state, NOT in DB; reset on refresh to `fitView()`). |
| Two-finger scroll (macOS trackpad) — `ctrlKey=false, deltaX!==0 \|\| deltaY!==0` on wheel | Pan by `{dx: -e.deltaX, dy: -e.deltaY}` (inverted scroll convention). Handoff L1982-1984. |
| Touch pan (single finger drag) | Not implemented Phase 2. Desktop-first per PROJECT.md. |

### 3. Zoom (CANV-04, CANV-06)

| Trigger | Behavior |
|---------|----------|
| `wheel` event with `ctrlKey === true` (trackpad pinch on macOS — browser synthesizes ctrlKey) OR `metaKey === true` (⌘+scroll) | Compute: `delta = -e.deltaY * 0.0015`. `newK = clamp(transform.k * (1 + delta), 0.25, 4)`. Cursor-anchored: `kRatio = newK / transform.k`, `x' = mx - (mx - transform.x) * kRatio`, `y' = my - (my - transform.y) * kRatio` where `mx/my` = pointer position relative to `canvasRef.getBoundingClientRect()`. |
| `addEventListener('wheel', handler, { passive: false })` | Required so `e.preventDefault()` can stop the browser's default scroll-page behavior. CANV-04. |
| Zoom clamp | Hard clamp at `[0.25, 4]`. Attempts to scroll past clamp: `newK = clamp(...)` which may equal current k — cursor-anchor math still runs but produces identity transform. **No bounce, no overshoot, no visual feedback.** (See Open Questions.) |
| Keyboard zoom | Not implemented Phase 2. Toolbar buttons land Phase 3 (TOOL-01); Phase 2 has no toolbar. |

### 4. Drag node (NODE-06)

| Trigger | Behavior |
|---------|----------|
| MouseDown on `.node` with `e.button === 0` (left click) | `onSelect(person.id)` first, then record `dragState = { id, startX: clientX, startY: clientY, origX: person.x, origY: person.y }`. Does NOT enter dragging mode yet. |
| MouseMove after MouseDown (≥ 3px from start in any direction) | Enter dragging: add `.dragging` class, set `cursor: grabbing`, `z-index: 100`, shadow jumps to `6px 6px 0 var(--ink)`. |
| MouseMove during drag | `setPerson({ x: origX + (clientX - startX) / transform.k, y: origY + (clientY - startY) / transform.k })`. Pure optimistic local update — NO server call, NO history commit. |
| MouseUp (end of drag) | **Drag-end commit:** (a) call `updatePerson(treeId, id, { x, y })` Server Action (b) save-pill on that person enters saving→saved (c) Phase 3 will wrap this in a zundo history entry per HIST-05. Phase 2 commits to server only, not to zundo. See Open Questions. |
| MouseUp before drag threshold (< 3px movement) | Treat as click (select only, no drag commit). |
| Escape during drag | Cancel: revert person.x/y to origX/origY, clear dragState. |

### 5. Selection (SEL-01, SEL-02, SEL-03)

| Trigger | Behavior |
|---------|----------|
| Click on `.node` | `selectedPersonId = person.id`. Visual: 2px accent border + accent shadow + 28×28 `+` button at bottom-center. Keyboard focus moves to the node (as `role="button" tabIndex=0`). |
| Click on same selected node | Toggle-off: `selectedPersonId = null`. Visual reverts. |
| Click on empty canvas | `selectedPersonId = null`. Visual reverts. |

### 7. Auto-save lifecycle (SAVE-01..04, ERR-01)

**State machine per person:**

```
       ┌──────── user types ───────┐
       ▼                           │
  ┌─────────┐  400ms idle   ┌───────────┐
  │  idle   │ ─────────────▶│ saving    │
  └─────────┘               └──────┬────┘
       ▲                           │
       │                     ACK   │   ERR
       │                    ┌──────┴──────┐
       │                    ▼             ▼
       │              ┌──────────┐  ┌──────────┐
       └─1.4s timeout─│  saved   │  │  error   │
                      └──────────┘  └─────┬────┘
                                          │
                                    Retry click
                                          │
                                          ▼
                                       saving
```

**Rules (locked):**

1. **Debounce: 400ms** of keyboard idle per field. Middle of REQUIREMENTS.md SAVE-01 "250-500ms" band. See Open Questions for override.
2. **Per-field debounce, per-person save queue.** Each field in the side panel has its own debounce timer; when any timer fires, all dirty fields for that person batch into ONE server call. This prevents race conditions where Name and Notes each fire their own request out-of-order.
3. **Serial per person.** If a save is in-flight and a new debounce fires, the new save waits (not cancels) — the pending payload is merged into a single follow-up. Never two concurrent requests to the same person. SAVE-04.
4. **Pill color timing:** `saving` shows IMMEDIATELY when the fetch starts (not when debounce starts — dirty→saving is the fetch-start edge). `saved` shows on 2xx response. `error` shows on 4xx/5xx/network. SAVE-02.
5. **Pill green persists 1.4s** then returns to `idle` (pill goes back to gray "Auto-saves"). If a new edit arrives during the 1.4s green window, go straight to `saving` (skip back to idle). SAVE-03.
6. **On unmount (panel close) with dirty fields:** Immediately flush the pending debounce. If the save fails after the panel is closed, a toast still surfaces.
7. **Optimistic local state:** All field edits update local state (and canvas rendering) immediately; server is eventually consistent via the pill. This matches PROJECT.md "Optimistic-local + authoritative-server" pattern.
8. **Drag save** is a separate channel from field-edit save but uses the same per-person serial queue. A drag-save in flight followed by a name-edit debounce → second request waits for the first.

**Pill visual mapping:**

| State | Dot color | Dot fill | Text | Text color | Border | Bg |
|-------|-----------|----------|------|------------|--------|-----|
| idle | `--ink-3` | solid | `Auto-saves` | `--ink-3` | `--rule` | `--bg-soft` |
| dirty | `--ink-3` | solid | `Auto-saves` | `--ink-3` | `--rule` | `--bg-soft` (no visual change — intentional) |
| saving | `--ink-3` | solid + pulse animation (1s infinite) | `Saving…` | `--ink-3` | `--rule` | `--bg-soft` |
| saved | `--success` | solid | `Saved` | `--success` | `--success` | `oklch(0.92 0.08 150)` |
| error | `--danger` | solid | `Couldn't save` (clickable) | `--danger` | `--danger` | `oklch(0.92 0.08 25)` |

### 8. Edge rendering (EDGE-01..06)

| Rule | Implementation |
|------|----------------|
| **Derived, never stored** — EDGE-01 | `computeEdges(people)` pure function. Returns `Array<{ kind: 'spouse' \| 'parent', a: PersonId, b: PersonId }>`. Dedupe spouse edges via sorted-pair key. Phase 2 copies the handoff `computeEdges` verbatim (model.jsx L45-62) into `lib/graph/edges.ts`. |
| **Single SVG overlay** — EDGE-02 | One `<svg class="edges" overflow="visible">` inside `.canvas-inner`, beneath the node layer (lower z-index). All edges as `<path>` children. |
| **SVG bbox** | Computed from `people[]` extents: `{ minX: min(p.x) - 400, minY: min(p.y) - 400, w: max(p.x) + NODE_W + 400 - minX, h: max(p.y) + NODE_H + 400 - minY }`. 400px padding ensures edge tails never clip. |
| **Spouse edge** — EDGE-03 | Horizontal straight line between the inner edges of two spouse cards at the same y. Path: `M ${a.x + NODE_W} ${a.y + NODE_H/2} L ${b.x} ${b.y + NODE_H/2}` (handoff `spousePath`). Stroke: 2px `--accent`. |
| **Parent-child edge** — EDGE-04 | Orthogonal 4-segment path from parent bottom center → horizontal midpoint between parent and child → down to child top center. Path: `M ${px} ${py} L ${px} ${mid} L ${cx} ${mid} L ${cx} ${cy}` (handoff `parentPath`). Stroke: 1.5px `--ink`. |
| **Parent-pair midpoint routing** | For children of a couple: route the parent-edge from the midpoint between the two parents' bottoms (not from a single parent). Phase 2 implementation detail: when both parents exist in `child.parentIds`, synthesize a virtual midpoint `(parentA.x + parentB.x + NODE_W) / 2` as the edge origin. This requires `computeEdges` to yield a "couple-child" edge type in addition to "parent-child" single-parent case. **Option: Phase 2 ships simple-parent edges (one edge per parent → child) and Phase 4's dagre layout adds the couple-merge optimization**. Recommendation: simple per-parent edges in Phase 2; Phase 4's dagre pass naturally produces the midpoint routing because couples become synthetic single nodes. See Open Questions. |
| **Non-scaling stroke** — EDGE-05 | `vector-effect="non-scaling-stroke"` on every `<path>`. Stroke width stays 1.5px / 2px regardless of zoom level k. |
| **60fps on 200 nodes** — EDGE-06 | Single SVG (one DOM element for all edges) + non-scaling-stroke + `overflow:visible` + `will-change: transform` on `.canvas-inner`. No virtualization in Phase 2 (200 nodes is within raw SVG perf budget). |

## Open Questions (for planner / checker / user)

These are defaults the researcher applied where REQUIREMENTS, handoff, and Phase 1 UI-SPEC did not converge. Each has a defensible default; flag to override.

1. **Topbar height conflict (52 vs 56).** Phase 1 locked 52px (handoff source). REQUIREMENTS.md CANV-01 + PANEL-02 say 56px. Phase 2 honors 52px. **Action:** update REQUIREMENTS.md Phase 2 section to match (mechanical edit — no UX impact), or override Phase 2 UI-SPEC to 56px. Recommended: keep 52px per DESIGN-03 pixel-parity mandate.

2. **Grid spacing 24px vs 8px.** REQUIREMENTS.md CANV-02 says "8px spacing, `--ink-4` at 10% opacity". Handoff `styles.css` says `--grid-size: 24px` using `--rule-soft` at full opacity. **Action:** spec follows handoff (24px, `--rule-soft`). `--ink-4` does not exist in the token system — this is a transcription error. Recommended: leave as 24px per handoff / DESIGN-03.

3. **Wheel-zoom sensitivity (0.0015 vs handoff 0.002).** Phase 2 proposes `0.0015` for smoother macOS trackpad feel. Mouse users may prefer `0.002`. Defer to empirical tuning in QA; shipping `0.0015` is acceptable. Flag for override if checker prefers handoff exact.

4. **Auto-save debounce (400ms).** Middle of REQUIREMENTS.md SAVE-01 "250-500ms" band. 400ms feels "instant enough" without hammering the server on long-form Notes typing. Alternatives: 300ms (snappier), 500ms (safer for slow connections). Flag for override.

5. **Drag persistence granularity.** Phase 2 commits drag to server on MouseUp only (drag-end). Not throttled during drag. Phase 5 broadcast will throttle to ~30Hz via a separate channel (RT-06) without changing persistence. Recommended: keep drag-end-only.

6. **Drag + history integration.** Phase 2 commits drag to SERVER but does NOT yet wire it into zundo's temporal stack. HIST-05 says "Drag ... commits exactly one history entry" — that is Phase 3 scope. Phase 2 responsibility ends at persistence; Phase 3 wraps mutations in `temporal` calls. Confirm this split is acceptable or whether Phase 2 should pre-wire zundo for drag/field-edit.

7. **Parent-edge routing for couples (simple vs midpoint).** REQUIREMENTS EDGE-04 says "parent-pair midpoint routing". Phase 2 default: render TWO edges (one per parent → child), which produces visually correct but duplicate strokes where the couple is horizontally adjacent. Phase 4's dagre pass with couple-merge naturally collapses to midpoint routing. Recommended: Phase 2 ships simple per-parent edges; Phase 4 delivers the couple-midpoint optimization. Confirm or override (override cost: ~40 LOC in `computeEdges` to synthesize midpoint geometry).

8. **Remove confirmation dialog (window.confirm vs styled modal).** Phase 3 PANEL-07 intent is a styled modal with "Remove" destructive button. Phase 2 scope has no modal infra. Recommended: ship `window.confirm` in Phase 2 and upgrade in Phase 3. Override: skip Remove in Phase 2 entirely (flag as Phase 3-only feature). Counter-argument for shipping confirm: users CAN delete mistakenly-added people in Phase 2 without blocking on Phase 3. Recommended to ship.

9. **Save pill "Saving" spinner.** Handoff has no animated spinner in the pill — just a static dot. Phase 2 spec proposes an optional 1s pulse animation on the dot during saving state. Flag: if checker prefers pure handoff parity, drop the pulse (just show text + static dot).

10. **Initial canvas transform for empty trees.** If `people.length === 1` (just the seed YOU), `{x: 400, y: 180, k: 1}` centers the YOU node acceptably. For `people.length > 1` (shouldn't exist entering Phase 2 from Phase 1, but defense-in-depth), the same default applies — the user can pan/zoom manually. Phase 3's Fit toolbar button will add bbox-aware fitting. Flag confirm: no Phase 2 bbox-fit.

11. **Zoom-clamp edge behavior.** When user scrolls past zoom limit: silent clamp (newK = oldK on overshoot). No visual "you can't zoom further" feedback. Accept as professional/Figma-like silent behavior.

12. **Node "+" button wiring in Phase 2.** The button is visible on selected nodes (NODE-05 requires it), but the radial menu it opens is Phase 3 (RAD-01). Phase 2 option (a): render the button and make click a no-op with a console log. Phase 2 option (b): hide the button until Phase 3. Recommended: (a) render but no-op, so the visual state machine (selection indicator) is feature-complete. Confirm.

13. **Pronouns field.** REQUIREMENTS.md PANEL-04 lists "pronouns free-text". Schema has no `pronouns` column in DATA-01 (it has `gender`, `birth_year`, `death_year`, `birth_place`, `notes` — **no pronouns**). **Action required:** either (a) add `pronouns text` column to `people` during Phase 2 planning (mini-migration), or (b) drop pronouns from the side panel until schema updated. Planning must resolve this.

14. **`birth_place` vs `location`.** Schema uses `birth_place` (DATA-01). Handoff side panel uses `Location` label and `person.location` field. REQUIREMENTS.md PANEL-05 lists "birth place". Resolution: UI label displays `LOCATION`, schema column is `birth_place`, React state key is `birthPlace`. Document mapping in planning.

15. **Phase 1 `SeedPersonNode` deletion vs coexistence.** Plan should explicitly remove `components/shell/SeedPersonNode.tsx` and `components/shell/GridBackground.tsx` (repurposed inside canvas-inner). Or keep SeedPersonNode aliased as `<PersonNode person={theOne} />` for the first-load case. Recommended: delete the shell versions and let `<PersonNode>` handle all cases including the lone is-me seed.
