# Phase 3 — UI Design Contract

> Visual and interaction contract for Phase 3 (Authoring & History). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Source of truth:** `design_handoff_family_tree/source/styles.css` (handoff `:root` CSS variables) + REQUIREMENTS.md RAD/ADD/HIST/TOOL/TOAST/SRCH/A11Y/PANEL-07 entries + Phase 2 UI-SPEC for inherited tokens. Per DESIGN-03 pixel-parity mandate, Tailwind v4 `@theme` maps handoff tokens 1:1 — no drift permitted.
>
> **Phase 3 UI surfaces in scope:**
> 1. Radial add menu — 4 buttons (Parent / Spouse / Child / Sibling) anchored on the selected node's `+` button, replacing the Phase 2 console.info no-op
> 2. Add-relative authoring loop — collision-nudge placement, auto-select, side panel auto-open, Name field auto-focus
> 3. Undo/redo via `zundo` temporal middleware — 100-entry cap, scope-aware shortcut (ignored in inputs/textareas), one-entry-per-action contract
> 4. Bottom-center floating toolbar pill — Undo / Redo / Zoom-out / Zoom% / Zoom-in / Fit / ✨ Tidy (disabled until Phase 4) / Panel toggle
> 5. Generic toast infra — replaces the Phase 2 hand-rolled `<SaveErrorToast>`-only pattern; supports save errors, action confirmations, and the Phase 3 inline-undo Delete pattern
> 6. ⌘K / ⌘F search palette — centered modal listing all people in the tree with avatar + relation hint, Enter selects + recenters, Esc dismisses
> 7. Inline-undo Delete — replaces Phase 2's `window.confirm()` gate on the SidePanel Remove button (PANEL-07 final form)
> 8. Reusable `.modal` primitive — backdrop dim + popIn keyframes; consumed by search palette in Phase 3, by Share modal in Phase 5
> 9. Accessibility sweep — focus rings on every new control, ARIA labels, scoped keyboard shortcuts, Tab order topbar → canvas → toolbar → side panel
>
> **Phase 3 surfaces OUT of scope (deferred):**
> - Tidy / dagre layout itself → Phase 4 (the toolbar Tidy button renders disabled in Phase 3; Phase 4 wires it)
> - Animated layout transitions → Phase 4
> - Share modal + invites → Phase 5 (uses the `.modal` primitive shipped here)
> - Realtime presence + cursors → Phase 5
> - Per-node arrow-key traversal → v2 (Out of Scope per PROJECT.md)
> - GEDCOM import/export → not in v1
> - Right-click context menus → v2 (RICH-02)

## Typography

Inherited from Phase 1 + 2; Phase 3 reuses only, no new sizes. Contract: **4 sizes (11 / 13 / 14 / 18) and 2 weights (400 / 600) — no exceptions.**

| Role | Font | Size | Weight | Line Height | Phase 3 usage |
|------|------|------|--------|-------------|---------------|
| Mono micro | JetBrains Mono | 11px | 400 | 1.2 | Toolbar zoom-readout; relation hint in search-palette result rows ("PARENT · OF YOU", uppercase 0.06em); **radial button caption labels (`PARENT`, `SPOUSE`, `CHILD`, `SIBLING`) — uppercase 0.08em tracking** |
| Label / emphasis | Inter | 13px | 600 | 1.3 | Toast Undo / Retry button label; search-palette empty-state heading (toolbar tooltip text exists only as `aria-label`, not a visible 13px element) |
| Body | Inter | 14px | 400 | 1.5 | Toast message text; search-palette result row name (primary); modal body paragraphs |
| Mono symbol | JetBrains Mono | 18px | 400 | 1 | Radial button center symbol (↑↔↓←) — visual prominence carried by the 18px size + JetBrains Mono geometry, not a weight bump |

**Toolbar buttons are icon-only.** No visible text label; lucide icon at 16px owns the glyph slot. Tooltip via `aria-label` only — visible tooltip on hover deferred to v2 (a `title` attribute is acceptable for v1 but not styled).

**Search-palette result hint:** mono 11px uppercase 0.06em — matches handoff `.role-select` letter-spacing. Format: `{RELATION} · {QUALIFIER}` where RELATION = one of `PARENT`, `SPOUSE`, `CHILD`, `SIBLING`, `SELF`, `RELATIVE`, and QUALIFIER is short context like `OF YOU`, `OF ALICE` for parents/spouses, omitted for distant relations. Example: `PARENT · OF YOU` for the user's parent.

**Radial button caption labels:** rendered at the same 11px Mono size as the relation hint, with `text-transform: uppercase` and `letter-spacing: 0.08em`. At 11px monospace inside a 56px button the four labels (`PARENT`, `SPOUSE`, `CHILD`, `SIBLING`) remain compact; the symbol-and-label vertical rhythm inside the button is symbol (18px) on top, label (11px) below, separated by the 4px label-to-symbol gap.

### Inline-undo delete color choice

The delete toast uses the standard ink-fill toast appearance — **NOT** danger red. Delete in Phase 3 is reversible (one click on Undo OR ⌘Z within 6 seconds OR via the normal undo stack later), so the visual register is informational, not alarming. Test this with users — if a user reports "I didn't realize I deleted Alice", the dwell can extend or copy can shift to "Removed Alice. Undo?" with an action prompt; the color does not need to change.

| Click Undo within 6s | Triggers `temporal.undo()` — the delete history entry pops; person reappears; relation arrays restore; selection moves back to the un-deleted person; side panel auto-reopens (matches the pre-delete UI state) |
| Press ⌘Z within 6s with focus outside an input | Same as clicking Undo — fires `temporal.undo()`; toast dismisses |
| Toast times out after 6s without action | Toast dismisses; the delete remains undoable via the normal undo stack (push has happened; `temporal.pastStates` retains it) |
| Re-clicking Undo on a stale toast | (Toast is dismissed before this can happen) |
| Self-delete attempt (`person.isMe === true`) | Remove button is hidden — same as Phase 2 PANEL-08 behavior |

**Critical contract:** the delete is committed to server + zundo IMMEDIATELY on Remove click. Undo from the toast is the SAME action as ⌘Z — it pops the history entry, which the temporal middleware persists back through a new server-action call. There is NO "soft-delete buffered for 6s" pattern; we ship optimistic-confirmed delete + immediately-undoable history.

### 3. Undo / redo & history (HIST-01..05)

| Trigger | Behavior |
|---------|----------|
| `⌘Z` / `Ctrl+Z` with focus NOT in input/textarea/contenteditable | Call `temporal.undo()`. Apply the prior `pastState` snapshot. Server resync: re-issue the inverse server-action calls per affected person. (Most ergonomic implementation: zundo restores the local Zustand state AND the temporal callback fires inverse operations to the server. Server may reject with constraint errors → toast surfaces.) |
| `⌘⇧Z` / `Ctrl+Shift+Z` / `⌘Y` / `Ctrl+Y` | `temporal.redo()`. Same server-resync pattern. |
| Shortcut fired with focus in `<input>`, `<textarea>`, or `[contenteditable="true"]` | NO-OP at the canvas level. Native input undo runs. HIST-04. Implementation: keyboard listener checks `document.activeElement?.tagName === 'INPUT' \|\| 'TEXTAREA' \|\| document.activeElement?.isContentEditable` and bails. |
| History cap | **100 entries** (locked from `<user_decisions>`). Configured via `temporal({ limit: 100 })`. Older entries silently dropped (FIFO). HIST-03. |
| What pushes ONE history entry (HIST-05) | Drag-end (single entry per drag gesture, captured on mouseup); field edit on blur (one entry per field-blur, even if user typed many keystrokes between focus-in and blur — debounce-then-blur acts as the commit boundary; intermediate keystrokes only optimistic-local update the store, not history); add-relative (one entry per radial pick); remove-person (one entry per Remove click); Tidy (Phase 4 — one entry per Tidy run). |
| What does NOT push history | Pan/zoom (transform is ephemeral), selection changes, side-panel open/close, radial open/close, search-palette open/close, toast dismiss, save-pill state changes. These are all in `partialize`'s exclusion list. |
| Drag intermediate movement | NO history push. PanZoomWrapper's `mousemove` listener calls `setPersonPosition` (which goes through a `temporal.pause()` / `temporal.resume()` bracket OR uses the `partialize` skip-pattern). Mouseup commits the final position with `temporal.resume()` then `temporal.pause(false)` so the single push captures the start-to-end snapshot. |
| Field edit history granularity | One entry per field-blur. If user types `Alice` in the Name field then tabs to Notes, ONE history entry captures the Name change. `useSaveQueue.flush(personId)` happens on blur AND on panel close — history push is wired into the same flush callback. |
| Saved-state preservation across undo | Yes: on undo, the affected people's pill flips to `Saving…` (server resync in flight) → `Saved` on ACK. The pill state is OUTSIDE history (`partialize` excludes `saveStateByPersonId`) so undo doesn't try to restore prior pill state. |
| ⌘Z behavior on the inline-undo delete toast (within 6s) | Same as clicking the toast Undo button — fires `temporal.undo()`. The toast's keyboard reachability is via Tab-to-Undo-button (toast is a sibling region), AND via the global ⌘Z shortcut.|
| Edge case: empty history | Undo / Redo buttons disabled (0.3 opacity). ⌘Z shortcut is a no-op. |

**Implementation note (zundo + drag coalescing):** The cleanest pattern is `temporal({ partialize: (state) => excludeEphemeral(state), equality: shallowEqual, limit: 100 })`. For drag specifically, wrap the entire drag gesture in `temporal.pause()` (entered on mousedown when drag threshold crossed) + `temporal.resume()` (entered on mouseup AFTER the final `setPersonPosition`). This causes ONE pastState push capturing the pre-drag→post-drag delta. Verify with the `temporal.pause()` API in zundo 2.x docs at plan time.

```
  partialize: (state) => ({
    people: state.people,
    // Exclude ALL ephemeral state from history snapshots:
    // selectedPersonId, sidePanelOpen, draggingPersonId, dragOrigin,
    // saveStateByPersonId, transform, radialOpenFor, searchOpen,
    // searchQuery, toasts, panZoomMode
  }),
  equality: shallow, // shallow equality on `people` map

```

The `partialize` config means only `people` (the relationship-bearing data) is in the history. Everything else is ephemeral and outside the undo stack.

## Open Questions (for planner / checker / user)

These are points where REQUIREMENTS, handoff, and `<user_decisions>` did not converge OR where the researcher is flagging a defensible default that should be confirmed.

1. **Toolbar border radius (0 vs 16).** REQUIREMENTS TOOL-01 says "16px radius". Handoff `.toolbar` does not set any `border-radius` (which CSS-defaults to 0) and the entire Swiss design system is 0-radius. Phase 3 honors handoff: 0px corners. **Action:** confirm or override. Recommended: 0 per DESIGN-03 + Phase 1/2 precedent. The 16px wording is likely a transcription error.

2. **Radial hover background (`--accent-soft` vs handoff `--ink` invert).** REQUIREMENTS RAD-02 says "hover fills with `--accent-soft`". Handoff `.radial-btn:hover` says `background: var(--ink); color: var(--bg);`. Phase 3 follows REQUIREMENTS authority. **Action:** confirm. The `--accent-soft` choice is softer and lighter than the handoff inversion; if user testing shows the radial slices feel "too quiet", swap back to handoff invert.

3. **Sibling button arrow direction.** Handoff implies left-positioned button uses `←`. `<additional_context>` says "← or →". Phase 3 ships `←` (matching the left position). **Action:** confirm or specify rightward arrow if there's a convention reason.

4. **Radial arrow keys (Tab cycle vs full arrow nav).** Phase 3 v1 ships Tab-cycle Parent → Spouse → Child → Sibling. Arrow keys (Up→Parent, Right→Spouse, Down→Child, Left→Sibling) are an enhancement that aligns with the radial's spatial layout but is optional for A11Y-01. **Action:** confirm Tab-only is sufficient, or upgrade to arrow-key spatial nav.

5. **Search palette: open the side panel after selection?** SRCH-02 says "selecting a result selects the person and recenters the canvas; closes palette." It does NOT say "opens side panel." Phase 3 ships pure select+center, no panel. **Action:** confirm. Counter-argument for opening the panel: user searched for someone presumably to edit them. Recommended: ship select+center only; user can double-click to open panel.

6. **Search palette result-row "relation hint" content.** Phase 3 spec proposes `{RELATION} · OF {QUALIFIER}` — e.g. `PARENT · OF YOU`. This requires walking the graph from the user's `is_me` person to compute the relation. Computational cost is small (BFS up to 4 hops). Alternative: skip the hint entirely, show only name + avatar. **Action:** confirm relation-hint implementation. Cost: ~30 LOC of relation-walking. If skipped, the result row is just avatar + name (40px row instead of 56px).

7. **Toolbar Panel-toggle disabled when no selection.** Phase 3 spec disables the panel-toggle button when `selectedPersonId === null`. Counter-argument: clicking the button could clear-and-then-toggle a default-selected person (e.g. the first node in the tree). Recommended: keep disabled — predictability matters more than convenience, and the user can click any node to enable the toggle.

8. **Inline-undo delete: does the toast persist if user navigates away mid-dwell?** If the user scrolls, opens search, or switches trees within the 6s window, the toast is mounted in the canvas root and persists (its timer keeps running). Recommended: keep mounted; tree-switch dismissess (different store instance). Confirm.

9. **Add-relative server failure rollback timing.** Phase 3 spec rolls back local state on server-action rejection. The rollback fires after the optimistic node is already visible (200-500ms typical roundtrip). User sees the new node briefly then it disappears. SaveErrorToast surfaces with Retry. **Action:** confirm "appear-then-vanish" UX is acceptable, or buffer the optimistic insert until ACK. Recommended: keep optimistic-first per existing Phase 2 pattern; the brief flash is acceptable feedback that something was attempted.

10. **History granularity for Notes (large textarea) edits.** A field-blur on Notes after typing 500 chars is ONE history entry (the whole 500-char delta). Undo restores the pre-typing state. Counter: some users expect granular undo within a textarea. Recommended: defer granular intra-textarea undo to native `<textarea>` undo (which still works because A11Y-02 keeps ⌘Z as input-scoped when focus is in textarea). The canvas-level history captures field-level deltas only. Confirm.

11. **Search palette: include the user themselves (is_me person)?** Phase 3 spec includes the `is_me` person in search results, labeled `SELF · YOU`. Counter: searching for yourself might be redundant. Recommended: include — there's no harm and it disambiguates if multiple people share a first name.

12. **Toast stacking limit (3 visible).** Phase 3 spec caps visible toasts at 3, auto-dismissing the oldest when a 4th arrives. Counter: a burst of save errors (network blip affecting 5+ pending saves) could lose error context. Recommended: keep cap at 3; merge save errors per-person at the publisher level (already in Phase 2 SaveErrorToast — surfaces ONE toast for the oldest-errored person, not one per error).

13. **Modal `top: 120px` on viewport heights below 600px.** A 120px top with a 60vh max-height result list can push the modal below the viewport on small screens. Recommended: clamp `top` to `min(120px, max(20px, vh * 0.15))` so the modal stays visible. Phase 3 spec ships pure 120px; flag for v2 polish.

14. **Tidy button visible-but-disabled vs hidden.** Phase 3 ships Tidy disabled (visible, opacity 0.3, no click handler) so the toolbar layout is final shape from day one. Counter: showing a non-functional button is visual noise. Recommended: keep visible-disabled; Phase 4 wires it without re-flowing the toolbar geometry.

15. **Fit-to-view button: reset-to-default vs bbox-fit.** Phase 3 ships REQUIREMENTS CANV-05 reset-to-default (`{x: 400, y: 180, k: 1}`), not bbox-aware fitting. A user with 100 nodes spread across the world won't see all of them after Fit. **Action:** confirm reset-to-default is acceptable for v1, or upgrade to bbox-fit. Recommended: ship reset-to-default per CANV-05; bbox-fit is a Phase 4 add (it's mentioned in the Phase 4 layout work).
